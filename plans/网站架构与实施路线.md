# 灵鸢实验室网站：架构与实施路线

版本：0.1 · 2026-09-28

## 1. 项目目标

灵鸢实验室是一个公开的学习与研究网站。从组织发展（OD）的经典知识出发，研究 AI 如何改变任务、协作、决策、组织设计与人才系统，并邀请读者讨论“AI 原生组织”可能出现的做法及其边界。

网站服务两类主要需求：**循序学懂** OD 与 AI 时代的组织知识；**拿去使用** 概念、问题清单和分析工具，审视真实工作场景。第一批读者是正在学习或实践 OD、HR、组织设计的人，以及关心人机协作的业务负责人和 AI 产品实践者。

“AI 原生组织”是研究问题，不是预设的标准答案。所有文章应区分研究证据、案例观察、作者推论和待验证假设。

## 2. 第一版范围

| 区域 | 第一版交付 |
| --- | --- |
| 首页 | 项目主张、四个入口、最新研究问题、从哪里开始 |
| 学习路径 | 八个连续主题，首发完成前两篇，其余以清楚的问题和阅读顺序展示 |
| 知识文章 | 有来源和版本信息的概念解释、研究文章、术语卡片 |
| 实践工具 | 与首发文章对应的两份可打印或复制的分析表 |
| 开放讨论 | 围绕预设研究问题提交观点或匿名案例；审核后公开展示和回应 |

讨论第一版无需读者注册。投稿先进入待审核状态，作者使用管理命令审核；公开页面只读取已审核内容。完整论坛、私信、个人主页和自动生成组织诊断结论不进入第一版。

首发的内容闭环是：**读一篇解释 → 看一张关系图 → 完成一份练习 → 对一个开放问题提出观点**。

## 4. 视觉方向

关键词：**轻盈、简洁、白色、未来感、有节制的彩色**。视觉表达应像一间开放的研究工作室，而不是企业后台或科幻仪表盘。

- 大面积白色与很浅的冷灰蓝留白；深墨色正文保持阅读对比度。
- 蓝、紫、青绿、暖橙作为章节和知识类别的识别色。彩色集中在路径节点、图解、标签及重点按钮，不铺满正文背景。
- 首页可用轻量的“知识轨道 / 关系网络”图形表达 OD → 工作 → AI → 组织的关联；内容页以清晰排版优先。
- 标题采用有个性的中英文字体组合，长文正文采用易读的中文无衬线字体。字体资源应尽量本地托管，并控制字体文件体积。
- 卡片细边框、柔和阴影、宽松间距、精确网格；动效只用于反馈和关系呈现，并尊重减少动态效果的系统设置。
- 现有 `assets/logo/lingyuan-logo.png` 是正式标志。它是深色透明底字标，优先用于浅色页面，保持原始比例。不要重绘字标或给它叠加渐变。

设计验收应覆盖手机、平板和桌面；中文长文阅读、键盘导航、焦点状态和文字对比度与美观同等重要。首批页面先做可点开的视觉样稿，再固定组件规则。

## 5. 技术架构

### 5.1 方案比较与选择

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Astro + FastAPI + PostgreSQL | 内容页轻、前后端边界明确，讨论数据独立管理 | 需要维护 TypeScript 与 Python 两套运行环境 | **采用** |
| Astro 单体 + PostgreSQL | 部署更少 | API、页面与内容审核容易混在一起 | 不符合本项目希望保持的严格目录边界 |
| Next.js + NestJS + PostgreSQL | 适合复杂交互和大型团队 | 对当前以阅读为主的网站偏重 | 留给未来确有复杂产品需求时再评估 |

Astro 内容集合用于保存和校验本地 Markdown/MDX 文章，公开阅读页在构建时生成；只给投稿表单和讨论列表加载必要的交互脚本。[Astro 官方文档](https://docs.astro.build/en/guides/content-collections/)说明了内容集合与 Markdown/MDX 渲染方式。FastAPI 独立提供讨论 API、输入校验和审核命令。PostgreSQL 只保存需要运行时写入的数据。

### 5.2 边界与数据流

```text
编辑文章/工具 → Git 中的内容文件 → Astro 构建 → 静态页面
读者投稿 → Astro 表单 → FastAPI /api/v1 → PostgreSQL（待审核）
作者审核 → 后端管理命令 → PostgreSQL（已发布）
读者浏览讨论 → 浏览器请求 /api/v1 → 已发布观点
```

前端不直接连接数据库；后端不负责渲染研究文章。两端通过版本化 JSON API 通信，生产环境经同域 `/api` 代理转发，避免跨域和多入口配置。发布前明确备份、迁移和恢复流程。

### 5.3 仓库目录

```text
frontend/                 Astro 站点、页面、组件、样式、内容集合
  src/content/            文章、术语、工具、研究问题的 Markdown/MDX
  src/pages/              路由
  src/components/         可复用的展示与交互组件
backend/                  FastAPI 应用、领域服务、API、审核命令、测试
database/                 PostgreSQL 初始化、迁移、种子数据、备份说明
deploy/                   Docker Compose、Caddy、发布脚本与运行说明
docs/                     长期有效的品牌与站点说明
plans/                    架构、阶段目标、验收标准
assets/logo/              用户选定的正式品牌标志
```

依赖方向：`frontend → API 契约 ← backend → database`。`database/` 拥有迁移文件；后端调用迁移，不在应用启动时隐式改表。文章与工具属于版本化出版内容，放在 `frontend/src/content/`，不复制进数据库。

### 5.4 数据模型与 API 边界

首版数据库至少包含：

- `discussion_topics`：研究问题标识、状态和排序；与内容文件中的公开问题 `slug` 对齐。
- `contributions`：问题标识、投稿正文、投稿类型（观点 / 匿名案例 / 反例）、审核状态、创建和公开时间。
- `moderation_events`：审核动作、时间和理由，便于回溯。

公开 API 限于读取已发布讨论，以及创建待审核投稿；管理审核不暴露为匿名接口。投稿限制长度、频率与内容类型，使用蜜罐字段和服务端限流减少垃圾内容。不要要求读者提交姓名或邮箱；投稿前提示不要写入可识别的组织和个人信息。数据库不保存不必要的个人资料。

## 6. 知识准确性与编辑规则

### 6.1 首批经典知识线索

| 主题 | 起始权威来源 | 使用方式 |
| --- | --- | --- |
| OD 与计划变革 | [Cummings & Worley, *Organization Development and Change*, 12th ed.](https://au.cengage.com/c/isbn/9780357986158/?filterBy=Higher-Education) | 建立诊断、干预、反馈的概念地图；注明教材版本 |
| 群体动力与社会变迁 | [Kurt Lewin, “Frontiers in Group Dynamics” (1947)](https://journals.sagepub.com/doi/abs/10.1177/001872674700100103) | 阅读原文及历史语境，不把复杂理论压成单一句式 |
| 组织设计的相互匹配 | [Jay Galbraith, Star Model](https://jaygalbraith.com/services/star-model/) | 理解战略、结构、流程、奖励、人员的联动 |
| 技术与社会系统 | [Trist & Bamforth, *Human Relations* (1951)](https://doi.org/10.1177/001872675100400101) | 讨论技术变化与工作群体安排的共同作用 |

AI 的当代观察从 [Microsoft 2026 Work Trend Index](https://www.microsoft.com/en-us/worklab/work-trend-index/agents-human-agency-and-the-opportunity-for-every-organization) 与 [Anthropic Economic Index（2026 年 6 月）](https://www.anthropic.com/research/economic-index-june-2026-report) 开始。两者提供不同样本与观察角度；每次引用都需写清采样对象、时间、测量口径、局限与厂商视角，不能直接推断所有组织的变化。

### 6.2 每篇文章的发布标准

1. 写出具体研究问题、场景与适用边界。
2. 定义关键术语，区分 OD、组织设计、工作设计以及 AI 工具、Agent 等概念。
3. 关键事实附原始来源；记录作者、标题、年份、版本、链接或 DOI、访问日期。
4. 为段落或结论标注「研究证据 / 案例观察 / 作者推论 / 待验证假设」。经典理论不等于对当代 AI 组织效果的实证证明。
5. 列出至少一个竞争性解释或反例，以及尚未解决的问题。
6. 默认由人逐条核对 AI 辅助整理出的事实、引文和数据；用户明确委托时可由模型使用工具逐条核对，保留原文位置、结论、修订与局限。01–02 课与 03–08 课分别获 2026-09-29、2026-09-30 委托；不发布查不到原文的引用，核对与发布授权分开。
7. 每次实质修订记录日期与变化；涉及企业实践时先获得授权并匿名化。

### 6.3 第一阶段八篇学习路线

| 顺序 | 研究问题 | 配套产出 |
| --- | --- | --- |
| 01 | OD 到底在改变什么？ | 概念文、术语卡、诊断问题清单 |
| 02 | 组织怎样运转？ | 要素关系图、组织观察表 |
| 03 | 任务、岗位、流程和结果有什么不同？ | 一个岗位的任务拆解模板 |

## 7. 实施阶段与验收

### 阶段 A：视觉与内容样板

- 产出首页、文章页、学习路径页的手机与桌面视觉样稿，确定色彩、字体、间距、图解语言和组件规则。
- 完成第 01 篇内容的来源核查及对应工具，让设计基于真实长文而非占位文本。
- 验收：能够从首页走到文章和工具；视觉符合白色、轻盈、彩色但克制的方向；品牌标志清晰。

### 阶段 B：可公开阅读的网站

- 建立 Astro 前端、内容集合、学习路径、文章模板、术语、工具箱与搜索/筛选的最小功能。
- 完成第 01、02 篇文章及两份对应工具；为每篇展示来源、证据状态和修订信息。
- 验收：手机和桌面可读；键盘可用；无横向溢出；阅读页不加载无关脚本；构建和链接检查通过。

### 阶段 C：可审核的研究讨论

- 建立 FastAPI、PostgreSQL、迁移与备份流程，接入问题页投稿和已审核观点展示。
- 完成审核命令、限流、错误提示和匿名信息提示。
- 验收：未审核投稿不公开；审核动作可追溯；接口异常时文章仍可正常阅读；测试覆盖投稿、审核与公开读取。

### 阶段 D：扩展与校正

- 沿八篇路线补全内容，根据真实读者问题完善术语、工具与讨论主题。
- 用读者的使用反馈检查学习路径是否有效，再决定是否需要账号、完整论坛或交互式分析工具。

## 8. 当前规划决策

- 中文为首发主语言；英文摘要可以随内容成熟后增加，不做双语并行发布门槛。
- 内容先由仓库文件管理，确保版本、来源和修订可追溯；讨论数据进入 PostgreSQL。
- 第一版讨论以审核后公开的投稿为主，保障研究质量与维护成本。
- 先完成真实内容和视觉样板，再扩展后端功能；前端、后端和数据库始终保持独立目录。
- 既有文字未来公开使用时保留 CC BY 4.0 署名原则；品牌名称和标志不按内容许可开放。正式上线时在站点提供完整许可说明。
