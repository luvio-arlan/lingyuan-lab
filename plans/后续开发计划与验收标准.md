## 0. 接手须知（必读）

### 0.1 阅读顺序

1. `plans/网站架构与实施路线.md`：产品目标、信息架构、视觉方向、技术选型、编辑规则。
2. `docs/品牌与标志规范.md`：唯一正式标志及使用方式。
3. 本文件第 1–4 节：现状、代码地图、不可破坏的约定、开发环境。
4. 选定一个工作包（第 5 节），读完它的“验收标准”再动手。

### 0.2 工作规则

- **一次只做一个工作包**，按第 5 节的顺序推进；前置条件不满足时不要跳做。
- **先读后改**：修改任何组件前，先读完该组件与使用它的页面。样式、动效、命名要与周围代码保持一致。
- **不要重做已完成的前端视觉**。用户已确认对现有前端满意。除第 5 节明确列出的修复项之外，不做风格性重构、不换字体、不换配色、不换动画库。
- **不编造事实与引用**。默认情况下，模型不得把来源的 `verified` 设为 `true`，也不得把文章 `status` 改为 `published`。第 01、02 课的 WP2 获用户于 2026-09-29 明确委托，允许用可复查的工具核对替代用户逐条阅读；其过程与证据必须记入 `plans/内容核对清单-01-02.md`。此例外不适用于后续课程。
- **不擅自提交或推送**。git 提交、创建远程仓库、部署上线都需要用户明确同意。
- **工作区中已有的删除**（`README.md`、`CONTRIBUTING.md`、`LICENSE.md`、旧版标志文件、`docs/第一阶段研究路线.md` 等显示为 `D`）是用户此前主动做的，**不要恢复**，除非用户要求。
- 每完成一个工作包，在本文件第 8 节“进度记录”追加一行：日期、工作包、结果、未决问题。

## 3. 不可破坏的约定

### 3.1 品牌

- 唯一正式标志：`assets/logo/lingyuan-logo.png`。**不得修改、重绘、叠加渐变或改变比例**。
- 网页使用 `scripts/prepare-brand.mjs` 的派生文件；需要新尺寸时改脚本，不要手工处理图片。
- 标志只用于浅色背景。深色区块（例如首页结尾的深色卡片）不放标志。

### 3.2 设计系统

- 颜色、字号、间距、圆角、阴影、缓动一律使用 `tokens.css` 中的变量；**组件中不得出现新的裸色值**（SVG 内部的 rgba 渐变装饰除外）。
- 类别色通过 `data-accent="blue|violet|teal|orange"` 注入 `--a / --a-ink / --a-soft`。文字用 `--a-ink`，图形用 `--a`，底色用 `--a-soft`。
- 固定的语义配色：
  - 知识轨道：OD＝蓝，工作＝青绿，AI＝紫，组织＝橙。
  - 入口：学习路径＝蓝，知识库＝紫，工具箱＝青绿，研究讨论＝橙。
  - 证据类型：研究证据＝蓝（实线），案例观察＝青绿（实线），作者推论＝紫（虚线），待验证假设＝橙（点线）。**不能只靠颜色区分**，线型也是标注的一部分。
- 字体：标题 `--f-display`（Instrument Serif + 思源宋体），正文 `--f-sans`（Inter + 系统中文无衬线），标签 `--f-mono`（Geist Mono），大号数字用 `.figure`。标题统一字重 500，配 `font-synthesis: none`。
- 新页面的页首使用 `PageHero`；卡片使用 `.card`，需要悬停光斑时加 `.spotlight`；按钮使用 `.btn`、`.btn-ghost`、`.btn-sm` 和 `Arrow` 组件。

### 3.3 动效

- 首页复杂动效集中在 `scripts/home.ts`，通过 `gsap.matchMedia` 限定为“允许动效”且“宽度 ≥ 961px、高度 ≥ 620px”才固定滚动；其余情况退化为静态布局。**新增固定区块不得超过现有的两个**。
- 内容页只用 `data-reveal`（IntersectionObserver + CSS），**不得引入 GSAP 或其他动画库**。
- 所有动画都要在 `prefers-reduced-motion: reduce` 下关闭或直接呈现最终状态，并保证内容不依赖动画才可见（无 JS 时 `data-reveal` 不隐藏，因为隐藏态依赖 `html.js`）。
- 跨页面过渡使用 CSS `@view-transition`。`view-transition-name` 在同一页面内必须唯一：文章标题用 `article-<id>`，问题标题用 `q-<id>`，页头用 `site-header`。

### 3.4 脚本与选择器

- 页头脚本占用了这些属性：`data-header`、`data-nav`、`data-pill`、`data-menu-toggle`、`data-sheet`。**其他组件不得复用这些名字**（此前工具页误用 `data-sheet` 已改为 `data-worksheet`）。
- 组件脚本用 `document.querySelector` 时，选择器要带组件前缀或限定在组件根节点内。
- 讨论内容一律用 `textContent` 渲染，**禁止 `innerHTML`**。

### 3.5 内容与编辑

- 遵守原路线 6.2 的七条发布标准。文章中每个判断性段落都要放进 `<Claim>`，研究证据要带 `n={来源序号}`。
- 来源的 `verified` 默认为 `false`；第 01、02 课按本次用户委托与核对清单处理，其余内容仍按人工核对规则。只有全部保留来源得到核对后，文章与工具才能改为 `published`。
- 示意性质的案例必须写明“（示意）”，不得伪装成真实观察。
- 涉及企业实践的内容先获授权并匿名化。

### 3.6 边界

- 依赖方向：`frontend → API 契约 ← backend → database`。前端不直连数据库；后端不渲染文章。
- 文章、工具、术语、研究问题的正文属于出版内容，留在 `frontend/src/content/`，**不复制进数据库**。数据库只保存讨论相关的运行时数据。

**验收标准**

### WP4 后端（`backend/`）

**前置**：WP3。

**目标**：实现讨论 API、输入校验、限流、审核命令与测试。

**决策**（如需变更，先征得用户同意）

- Python 3.12+，用 `uv` 管理依赖；FastAPI、pydantic v2、pydantic-settings、psycopg 3（连接池，直接写 SQL，不使用会自动建表的 ORM）、typer（管理命令）。
- 质量工具：ruff（lint 与格式化）、pyright 或 mypy、pytest、httpx。
- 建议结构：

```text
backend/
  pyproject.toml
  src/lingyuan_api/
    main.py            create_app()；挂载 /api/v1；启动时检查迁移版本，未迁移则拒绝启动并给出明确提示
    config.py          DATABASE_URL、RATE_LIMIT_*、BODY_MIN/MAX、TRUSTED_PROXY 等
    db.py              连接池
    schemas.py         请求与响应模型
    domain/            投稿与审核的业务规则（纯函数与服务）
    repositories/      SQL 读写
    api/v1/            路由：health、topics/{slug}/contributions
    ratelimit.py       限流
    admin/cli.py       管理命令（lingyuan-admin）
  tests/
```

**接口**：完整规格见附录 A。前端客户端 `frontend/src/lib/api.ts` 已按该契约实现，**后端必须兼容它**；如需修改契约，必须同时修改 `api.ts` 并在附录 A 记录版本变化。

**管理命令**（不暴露为 HTTP 接口）

```text
lingyuan-admin migrate                       执行 database/migrations 中未应用的迁移
lingyuan-admin sync-topics PATH              从前端 questions 目录同步问题 slug 与 state（open/planned），以及 sort_order
lingyuan-admin pending [--topic SLUG]        列出待审核投稿
lingyuan-admin show ID                       查看一条投稿
lingyuan-admin publish ID [--response TEXT]  发布（可同时附实验室回应）
lingyuan-admin reject ID --reason TEXT       拒绝（必须填写理由）
lingyuan-admin respond ID --text TEXT        为已发布投稿添加或修改实验室回应
lingyuan-admin unpublish ID --reason TEXT    撤回已发布投稿（状态改为 rejected）
```

每个改变状态的命令都必须**在同一事务中**写入 `moderation_events`，`actor` 取自 `--actor` 参数或环境变量 `LINGYUAN_ACTOR`，两者都没有时拒绝执行。

**安全与反垃圾**

- 只接受 `application/json`，请求体不超过 16 KB。
- 正文：去掉首尾空白，做 NFC 规范化，移除控制字符（保留换行）；按 Unicode 字符数计算长度（20–2000）。
- 蜜罐字段 `website` 非空时：返回与正常提交相同的 201 响应，但**不落库**，只在日志中计数。
- 限流：同一客户端每 10 分钟最多 5 次、每天最多 20 次投稿；单个问题每小时最多 60 次。客户端标识使用“加盐哈希后的 IP”，只保存在内存中，不写入数据库或日志。只有配置了 `TRUSTED_PROXY` 时才信任 `X-Forwarded-For`。v1 以单进程运行，重启后计数清零可以接受；以后改为多进程时，需要改用共享存储。
- 只对 `state='open'` 的问题接受投稿，否则返回 409；不存在的问题返回 404。
- 同源部署，不开启 CORS。
- 日志中不记录投稿正文和 IP。

**验收标准**

- [x] `uv run pytest` 全部通过，测试运行在真实的 PostgreSQL 上（本机临时 PostgreSQL 16 实例），覆盖：
  - 创建投稿：成功（201、状态为 pending）；422（过短、过长、未知 kind、损坏的 JSON）；非 JSON 媒体类型 415；404；409；429；蜜罐（返回 201 但数据库无记录）。
  - 公开读取：只返回 `published`；按 `published_at` 倒序；`pending` 和 `rejected` 永远不出现；字段与附录 A 一致。
  - 审核：publish、reject、respond、unpublish 都会产生 `moderation_events` 记录，状态与 `published_at` 同步变化；缺少 actor 或 reject 缺少理由时失败；事务失败时不留下半完成状态。
  - 迁移：未迁移时应用拒绝启动，并给出提示。
- [x] `ruff check`、`ruff format --check` 与类型检查 0 错误。
- [x] `GET /api/v1/health` 在数据库可用时返回 200 `{"status":"ok"}`，数据库不可用时返回 503。
- [x] 手动验证：前端开发服务器通过代理连接本地后端，在问题页提交一条投稿，显示“已收到”；用 `lingyuan-admin publish` 发布后，刷新页面能在“读者投稿”中看到，内容以纯文本显示（在正文中写 `<script>` 不会执行）。

```json
}
```

- 排序：`published_at` 倒序；每页最多 50 条。`next_cursor` 为 v1 预留字段，前端暂不使用。
- `404`：问题不存在。`planned` 状态的问题返回 `200` 与空列表。
- `kind` 取值：`opinion`（观点）、`case`（匿名案例）、`counterexample`（反例）。

### A.2 创建投稿

`POST /api/v1/topics/{slug}/contributions`

请求体：

```json
{ "kind": "opinion", "body": "20–2000 个字符", "website": "" }
```

| 状态 | 含义 | 响应体 |
| --- | --- | --- |
| 201 | 已进入待审核（蜜罐命中时同样返回 201，但不保存） | `{"id": "<uuid>", "status": "pending"}` |
| 404 | 问题不存在 | 错误体 |
| 409 | 问题未开放投稿 | 错误体 |
| 413 | 请求体过大 | 错误体 |
| 415 | 不是 JSON | 错误体 |
| 422 | 校验失败 | 错误体，`details` 指明字段 |
| 429 | 超出频率限制 | 错误体，并带 `Retry-After` 响应头 |

错误体统一格式：

```json
{ "error": { "code": "rate_limited", "message": "提交太频繁了，请稍后再试。", "details": null } }
```

### A.3 健康检查

`GET /api/v1/health` → `200 {"status":"ok"}`；数据库不可用时返回 `503 {"status":"degraded"}`。

### A.4 前端现状

`frontend/src/lib/api.ts` 已实现 A.1 与 A.2，8 秒超时，非 JSON 响应视为错误。WP1 需要补上对 404 和 409 的文案处理。契约若有变化，前后端同时修改，并在此处记录版本。

## 附录 B：数据库 DDL 草案（`0001_init.sql`）

```sql
CREATE TABLE schema_migrations (
  version    text PRIMARY KEY,
  applied_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE discussion_topics (
  slug       text PRIMARY KEY CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  state      text NOT NULL CHECK (state IN ('open', 'planned', 'closed')),
  sort_order integer NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE contributions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  topic_slug   text NOT NULL REFERENCES discussion_topics (slug) ON UPDATE CASCADE,
  kind         text NOT NULL CHECK (kind IN ('opinion', 'case', 'counterexample')),
  body         text NOT NULL CHECK (char_length(body) BETWEEN 20 AND 2000),
  status       text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'published', 'rejected')),
  lab_response text CHECK (lab_response IS NULL OR char_length(lab_response) <= 2000),
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  CHECK ((status = 'published') = (published_at IS NOT NULL))
);

CREATE INDEX contributions_public_idx
  ON contributions (topic_slug, published_at DESC) WHERE status = 'published';
CREATE INDEX contributions_pending_idx
  ON contributions (created_at) WHERE status = 'pending';

CREATE TABLE moderation_events (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  contribution_id uuid NOT NULL REFERENCES contributions (id) ON DELETE RESTRICT,
  action          text NOT NULL CHECK (action IN ('publish', 'reject', 'respond', 'unpublish')),
  reason          text,
  actor           text NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  CHECK (action NOT IN ('reject', 'unpublish') OR reason IS NOT NULL)
);
```

说明：`closed` 状态为以后关闭讨论预留，前端内容集合目前只有 `open` 和 `planned`。

## 附录 D：来源核对协议

1. **谁核对**：通常由用户人工核对。第 01、02 课是用户于 2026-09-29 明确委托的例外，由模型使用工具核对；证据和局限见 `plans/内容核对清单-01-02.md`。
2. **核对什么**：作者、标题、年份、版本、卷期页码、DOI 或链接能否打开；引文措辞与原文是否一致；转述是否忠实；是否把经典理论误用为对当代 AI 组织效果的证明。
3. **怎么记录**：在 `plans/内容核对清单-<课号>.md` 中逐条记录：核对日期、原文位置（页码或章节）、结论（一致 / 需修订 / 查不到）、修订内容。
4. **结果处理**：一致 → `verified: true`；需修订 → 先改正文，再标记为已核对；查不到 → 删除该引用，或把相关段落改为 `inference` / `hypothesis` 并去掉来源序号。
5. **发布**：一篇文章的所有保留来源都核对完成后，才可在用户同意下改为 `status: published`，同时在 `revisions` 中记录。第 01、02 课的本次委托包含此项授权；后续课程仍须另行确认。
